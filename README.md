# HRMS

An internal Human Resource Management System for a single organization, running as one Cloudflare Worker:
a React SPA served as static assets, a strictly **AEP (aep.dev) resource-oriented** JSON API on `/v1/*`,
D1 for data, R2 for documents, and Google sign-in. Shaped throughout for Cloudflare's free-tier budgets
(no KV, no Queues, batched D1 access).

Scale today: 92 collections over 100 tables, 106 route files (78 of them generated by the collection
factory), 112 services, 67 SPA pages, 110 test files / 1252 tests.

## What it does

**Home** - dashboard with pinnable widgets, unified approvals inbox (bulk approve/reject), self-service
profile.

**Workforce**
- *Team*: employee directory and profiles, org chart with drag-to-reparent, onboarding and offboarding
  transitions with task templates, background checks.
- *Progress*: kanban boards with sprints and CFD/lead/cycle analytics, goals with alignment and rollup,
  review cycles with 360 feedback and calibration, 1:1 check-ins.
- *Connect*: announcement feed with reactions, replies, polls and read receipts; suggestion box with
  anonymity and upvotes; events; kudos wall.
- *Hiring*: full ATS - requisitions, candidates, application pipeline, interviews and scorecards, offers,
  candidate-to-employee conversion, referrals with tiered milestone bonuses, recruiting analytics.

**Employment**
- *Time*: attendance with regularization requests, shift scheduling and rosters, project timesheets,
  overtime, remote work, approval delegation.
- *Leave*: requests with approve/reject/cancel, prorated monthly accrual, carry-forward, encashment,
  calendar view, fixed and optional holidays.
- *Pay*: payslips, reimbursements, loans with EMI recovery, tax declarations with verification, benefit
  plans and enrollments.
- *Payroll*: pay components, pay periods, bonuses, salary structures and pay grades, CTC splits, statutory
  deductions (EPF/ESI/PT/TDS with employer contributions), full-and-final settlements, bank files,
  Form 16, run state machine `DRAFT → REVIEW → APPROVED → LOCKED → PUBLISHED` with staleness detection.

**Company** - org and personal documents with acknowledgement/e-signature, operational expenses with
vendors, categories, budgets and recurring runs, compliance calendar with recurrence rules, asset tracking
with printable QR/Code128 tags and a stocktake scanner.

**Admin** - workflow engine (event bus + data-driven automation rules, scheduled and recurring triggers,
in-app and email actions), activity/audit log, and Settings covering every configurable surface.

**Platform** - access control as one fail-closed middleware over policy stored as data; lifecycle
(soft delete/restore, purge, enable/disable, lock/unlock, draft/publish) on every record; letter and
payslip PDF generation with e-signature; global ⌘K search over FTS5; in-app notifications and opt-in web
push; PWA install; CSV/Excel export; saved table views; API keys for machine callers; "view as" simulation.

## Running locally

One command brings up the whole stack (D1, Worker, Prism contract proxy, Vite):

```bash
npm install
scripts/start.sh --demo      # fresh local DB: production catalog + demo people, logs you in as super_admin
scripts/start.sh             # subsequent runs, acting as super@example.com
scripts/start.sh hr@example.com   # act as another seeded role
```

Or run the three processes by hand:

```bash
npm run db:migrate:local
npm run dev        # worker on :8787       (terminal 1)
npm run dev:proxy  # Prism contract proxy on :4010 -> :8787   (terminal 2)
npm run dev:web    # Vite SPA on :5173 -> :4010               (terminal 3)
```

Open the SPA on **:5173**. It proxies through the contract validator on **:4010**; never hit the Worker on
:8787 directly, or contract drift goes unnoticed. Local auth is faked by `DEV_FAKE_EMAIL` in `.dev.vars`,
which only works together with `ALLOW_DEV_AUTH=true`.

## Working in this repo

- **One gate:** `npm run verify` (`api:lint` at `--fail-severity=warn`, then `typecheck`, then `test`). It
  runs as a pre-commit hook and in CI (`.github/workflows/verify.yml`), and must be green before anything
  moves.
- **Contract first:** add or change an endpoint in `openapi.yaml`, run `npm run api:types`, then implement.
  `openapiRoutesDrift` and `customMethodsDrift` fail when code and contract disagree.
- **Collections:** there is exactly one way to build one - write a spec, mount it
  (`docs/03-add-a-resource.md`). `test/collectionLaneDrift.test.ts` fails a hand-rolled standard method.
- **Access control is data, not code.** Never add a check in a service or route; change grants, access
  rules or the policy manifest instead (`docs/authz.md`).
- **Migrations:** the project is greenfield and keeps exactly ONE migration. After a schema change, squash
  back to `0000` (remove the sql + meta snapshot, empty the journal, `npm run db:generate`).
- Tests: `npm test`. If it reports "no tests" with an `EPERM` on `.dev.vars`, the command sandbox denied the
  file - rerun outside it (see `docs/04-testing.md`).

## Deploying

`docs/deploy.md` is the runbook: provision D1/R2, choose the auth mode, set secrets, seed
`bootstrap/bootstrap.sql` (never the demo seed), deploy, grant the break-glass super admin.
`docs/deploy-security.md` is the security checklist that goes with it. Open items before a first production
deploy are tracked in `production-readiness.md`.

> Scope guard: this system computes compensation, statutory deductions and payslips for a **single
> jurisdiction (India)** and a single currency. It does not move money or file with authorities. See
> `docs/architecture-decisions.md`.
