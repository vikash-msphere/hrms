Runtime, committed

wrangler.toml [vars]

Bindings, cron triggers and non-secret vars. In git, edited in your editor. Changing one needs a redeploy. The Cloudflare dashboard will let you edit these, and the next deploy overwrites it.

Runtime, secret

wrangler secret put

Stored on the Worker, never in git, never in CI. Cloudflare → Workers & Pages → hrms → Settings → Variables and Secrets does the same thing in a browser. Persists across deploys on its own.

Baked into the bundle

web/.env → VITE_*

Read by Vite at build time and compiled into the JavaScript. Public, and committed here on purpose. A missing one needs a new build, not a secret.

CI only

GitHub → Settings → Environments → production

Credentials and acknowledgements the deploy and backup workflows use. Secrets on the Environment secrets list, non-secret ones on Environment variables. They never reach the Worker.

Bindings

wrangler.toml · committed

Set where: provision the resource first (wrangler d1 create hrms, wrangler r2 bucket create hrms, wrangler vectorize create hrms-search), then paste the id into wrangler.toml in the repo and commit it. Cloudflare → Workers & Pages → hrms → Settings → Bindings shows what is deployed; it is not where you edit them, because the next wrangler deploy replaces the whole list with this file.

Required secrets

wrangler secret put · never committed

Set where: npx wrangler secret put NAME from the repo root (add --config wrangler.staging.toml for the hrms-staging worker — a secret does not travel between the two), or Cloudflare dashboard → Workers & Pages → hrms → Settings → Variables and Secrets → Add → type Secret. Either way they live on the Worker and survive redeploys, so they are set once and never put in GitHub. Generate fresh values for production — never reuse anything from .dev.vars.

Optional secrets

wrangler secret put · feature switches

Set where: same place as the required ones — npx wrangler secret put NAME, or Workers & Pages → hrms → Settings → Variables and Secrets. Absent by default. Each one turns a feature on; leaving it unset degrades gracefully rather than erroring.

Worker vars

wrangler.toml [vars] · committed, not secret

Set where: the [vars] block of wrangler.toml in the repo, then commit and deploy. Not in the Cloudflare dashboard: Workers & Pages → hrms → Settings → Variables and Secrets will accept a plaintext edit there, and the next wrangler deploy replaces the whole set with this file, so a dashboard-only value disappears at the next release with nothing to show for it. Staging has its own copy of this block in wrangler.staging.toml: the two files share nothing, so a var added here and not there simply does not exist in a rehearsal.

SPA build values

web/.env · compiled into the bundle by Vite

Set where: web/.env in the repo, which is committed on purpose — nothing in it is a secret, and a committed copy is what makes a CI build reproducible from a clean checkout. Edit that file, not web/.env.example (which documents the keys), and not Cloudflare or GitHub: these never reach the Worker at all. Public by construction — never put a secret here. A value missing at build time cannot be supplied later by a Worker secret; it needs another build. A fork deploying its own instance must replace the DSN and the VAPID public key with its own, or its reports and push subscriptions land on this organisation's.

CI / build-machine variables

GitHub → Settings → Secrets and variables → Actions → Variables

Set where: GitHub repository → Settings → Secrets and variables → Actions → the Variables tab (or Settings → Environments → production → Environment variables, which the deploy job resolves the same way). deploy.yml reads them as ${{ vars.NAME }} and passes them to npm run preflight and npm run build:web as process environment. Deploying by hand, export them in your shell instead. Read by web/vite.config.ts and scripts/preflight.ts; not VITE_-prefixed, so none of these reach the bundle, and none of them reach the Worker either.

GitHub repository secrets

Settings → Environments → production → Environment secrets

Set where: GitHub repository → Settings → Environments → production → Environment secrets (all three workflows declare environment: production, so that is the scope they resolve in; repository-level Actions secrets work too). Used by deploy.yml, d1-backup.yml and r2-backup.yml. No application secret belongs here — those live on the Worker and persist across deploys.

Confirm these are absent

verify on the Worker before go-live

Check where: wrangler.toml (preflight reads it and will fail the deploy for most of these), and Cloudflare → Workers & Pages → hrms → Settings → Variables and Secrets, which preflight cannot see — a value added by hand in the dashboard, or a stray wrangler deploy --var, is exactly what the file-level checks miss. Not things to set: things to check are not set. Tick each once you have confirmed it.

Values that must match across lanes

Each pair spans two different places, so neither half can validate the other at deploy time. These are the mismatches that ship green and fail silently.

VITE_SENTRY_DSNmust equalSENTRY_DSN The /diag relay only forwards envelopes addressed to its own DSN. A mismatch drops every report from the SPA with no error anywhere.
VITE_VAPID_PUBLIC_KEYmust equalVAPID_PUBLIC_KEY Wrangler never reveals a secret, so preflight validates only the shape of the build-side key. Verify the pairing after deploy: enable notifications on one device and watch wrangler tail for a 401.
VITE_APP_VERSIONmust equalSENTRY_RELEASE Both halves of a distributed trace need the same release string, or the client and server sides of one incident land on different releases and the source maps match neither.
GOOGLE_CLIENT_IDredirect URIhttps://<host>/auth/callback Registered in the Google Cloud console, per hostname. Add the staging host as a second authorized redirect URI at the same time.
EMAIL_FROMverified atEMAIL_PROVIDER The sending domain has to be verified with the vendor before anything sends. One message to a real inbox is the cheapest proof: node --import ./scripts/tsResolve.mjs scripts/testEmail.ts you@example.com.
hrms-search --dimensionsmust equaldomain/aiPolicy.ts embedding model The index is created once with a width and a metric, and vectors from two models are not comparable — change either and the index has to be rebuilt. Staging must point at hrms-search-staging, never production's: it runs on a copy of the database with different record ids, so a shared index means staging's upserts overwriting production's rows.
